## 1. 当前交付与未来工程的边界

本轮只整理可在 Windows 上落地的项目规划。当前机器为 macOS，没有本项目所需的 RPG Maker MZ 或 Godot 开发资源，因此不创建、运行或发布引擎工程。

正式游戏采用固定主角、七章人生叙事、正交地图与侧视回合战斗。主线保底队伍为林恩与赫岚，战斗上场最多四人；其余同伴在安全据点换队。第一版使用 RPG Maker MZ；Godot 4 稳定版是一次性改选的备选路线，不同时维护两个游戏工程。

本仓库现有 React 游戏提供设计素材：七章主题、长期因果、目标战斗、年表、战败重试和多结局思路。新工程不自动迁移 React 组件、卡牌循环、网页运行时、浏览器存档、Docker 发布流程或原作立绘。96 张卡牌的效果需要重新设计成技艺与装备，不能把原数值直接复制进数据库。

## 2. 引擎路线与冻结点

### 2.1 主路线：RPG Maker MZ

MZ 承担地图编辑、事件编排、数据库、消息窗口、队伍、回合战斗和基础存档。项目代码集中在两个自有插件中，不另外建立一套 JavaScript 游戏引擎。插件在 MZ 的插件管理器中启用并配置，官方提供原生插件管理与资源管理入口。[MZ 辅助工具与插件管理](https://rpgmakerofficial.com/product/MZ_help-en/01_05.html)

| 能力 | 实现位置 | 约束 |
| --- | --- | --- |
| 地图移动、碰撞、门、调查与对话 | 地图事件、事件页、自开关 | 普通场景不写散落的脚本调用 |
| 技艺、物品、敌人、装备与状态 | 原生数据库 | 数值、图标、说明和可用场合集中定义 |
| 七章推进、时间跳跃、角色外观切换 | 公共事件＋剧情插件命令 | 章节交接统一入口，不能由多个地图各自推进 |
| 队伍与换队 | 原生队伍＋剧情插件的人物状态约束 | 地图人物状态与战斗人物状态一致 |
| 任务、具体事实、人物档案、年表 | `EmbersStory.js` | 一个权威剧情状态，不与开关各自维护一份逻辑 |
| 五类战斗目标、敌方预告、固定行动顺序、重试 | `EmbersBattle.js` | 挂接默认战斗流程，不改写整个战斗场景 |
| 钱币和普通掉落 | 原生战斗奖励 | 特殊任务奖励另走一次性剧情结算；等级使用原生经验曲线与主线最低等级保底 |
| 五个手动槽位、独立自动槽位及保存失败处理 | 原生存档入口＋剧情插件适配 | 战斗中禁用存档；手动槽位不能被自动存档覆盖 |
| 设置、标题、结束与读档 | 原生菜单及必要窗口扩展 | 不重建全部基础界面 |

默认战斗模式选择标准回合制，不选择 TPB。无额外行动次数特性；命中随机、伤害浮动、暴击默认关闭。战斗插件移除原生行动速度随机扰动，以敏捷排序，同敏捷依次按队伍阵位 1–4、敌群位置 1–4 排序。敌方目标与分阶段动作由遭遇定义确定，实际伤害仍使用原生伤害与状态结算。

所有敌群原生 EXP 为 0；主线首次胜利在公共事件中按最低等级表补足原生经验，可选战斗不发经验。等级保底、钱币和普通掉落各自只结算一次。

### 2.2 改选评审只发生在技术原型结束时

先实现一张测试地图和可复用的目标战斗原型，再决定是否保留 MZ。评审位于大批量地图、角色动画和章节事件制作之前。

保留 MZ 的条件：四人战斗、护送独立 HP、任务目标、年表与存档通过小范围钩子即可完成；地图与事件编辑仍然是主要内容工作。改选 Godot 的触发条件：上述能力必须持续替换默认战斗生命周期，或既定界面与目标战斗在插件结构下反复产生不可控冲突。

改选需要记录原因、弃用内容和新增工作量。可保留的内容是文字、稳定 ID、逻辑规则、数值表、原创素材源文件及授权台账；MZ 地图、事件页、公共事件和插件不是自动迁移对象。发生改选后停止 MZ 新增功能，Godot 从最小原型重新完成同一试玩，不保持两条并行发布线。

### 2.3 Godot 备选的模块对应

若改选，使用开发启动时可取得的 Godot 4 稳定版本、GDScript、2D 正交地图和 Compatibility 渲染。编辑器版本与导出模板必须一致并冻结；不承诺某个未来“最新版”或未经实际机器确认的最低硬件配置。

| MZ 能力 | Godot 对应模块 |
| --- | --- |
| 地图事件、传送与调查 | 地图场景、TileMapLayer、交互对象与区域触发 |
| 数据库 | 以稳定 ID 标识的 JSON 定义与 GDScript 读取适配 |
| 公共剧情事件 | `StoryState` 与任务流程调度，信号通知界面 |
| 战斗与目标插件 | 独立 `BattleScene`、回合调度、目标控制器 |
| 敌方意图 | 行动计划数据及战斗 HUD，不通过模拟消耗正式状态 |
| 任务／人物／年表窗口 | 共用状态源的 Control 界面 |
| 原生存档适配 | `SaveService`，使用 `user://` 路径、临时写入后替换 |
| Windows 发布 | Windows Desktop 导出预设及匹配模板 |

Windows 导出使用引擎导出系统生成运行程序与游戏数据；默认面向 x86_64，其他架构不纳入首发范围。[Godot Windows 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_windows.html)

## 3. Windows 工作目录、版本与协作

### 3.1 未来建立的目录

工作目录采用简短英文路径，例如 `D:\Games\Embers`。这是未来 Windows 目录示例，不是当前 macOS 文件路径。

```text
Embers/
  design/                 已冻结的设计、内容与数值表
  mz-project/             RPG Maker MZ 工程
  source-assets/          美术、音乐、音效源文件
  asset-register/         素材授权、作者与用途台账
  releases/               导出包与版本说明，不混入源工程
```

MZ 工程保留编辑器生成的原始目录结构：项目文件、`data/`、`js/`、`img/`、`audio/`、`effects/`。自有插件位于 `js/plugins/`；自定义登记表为 `data/EmbersRegistry.json`。资源通过规定目录导入，不能直接把网页里的 WebP、CSS、SVG 回退图或 TypeScript 文件放入运行工程当作兼容资源。

素材源文件与正式导出资源分开保存。临时生成图、截图和设计参考不进入运行资源目录；运行目录只保留清单中使用的最终或明确标为占位的文件。

### 3.2 安装与空工程建立顺序

1. 在未来 Windows 开发机合法安装 RPG Maker MZ；按实际购买渠道保留购买与资源使用凭据。
2. 根据该版本官方要求确认操作系统、显示、内存与磁盘条件；记录实际开发机配置，不用本文推断最低配置。
3. 使用编辑器“新建项目”建立空工程，不复制他人安装目录、商用运行库或不明来源整包。
4. 记录编辑器版本、工程运行核心版本、官方插件版本；在首次里程碑结束后冻结。
5. 设置侧视、标准回合制、中文标题、初始地图、角色与五个手动存档位。
6. 从本规划登记首批内容 ID，再导入具备授权记录的占位资源；最后启用两项自有插件。
7. 原型通过后保存带版本标签的基础工程，内容制作从该基线继续。

MZ 运行游戏并不要求玩家安装编辑器；未来发布仍需按购买版本的许可范围分发其允许的游戏运行文件。[关于 RPG Maker MZ](https://rpgmakerofficial.com/product/MZ_help-en/01_01.html)

### 3.3 Git 与文件所有权

- 新引擎工程独立于当前 React 项目，建立专用 Git 仓库；当前仓库继续保存规划与旧原型，不改变其运行方式。
- 提交设计、插件、数据库 JSON、地图、资源导出清单与版本锁定记录；不提交个人存档、缓存、导出包或密钥。
- 大型素材源文件使用 Git LFS 或独立版本化素材库，二选一并在工程建立时固定；默认选择 Git LFS，不把其当作素材备份的唯一副本。
- 分支按里程碑或章节组织，例如 `prototype`、`demo`、`chapter-03`；版本标签对应完整可交付包，不在未完成章节上标记正式版本。
- 同一地图、数据库类别或公共事件列表在同一时间只由一个人编辑。MZ 数值 ID 及地图事件 JSON 的冲突不能仅靠 Git 文本合并解决。
- 编辑器／运行核心升级只安排在里程碑边界；先保留旧版本备份，再做兼容验收，禁止制作过程中自动跟随升级。

## 4. 内容登记、数据库与事件编排

### 4.1 稳定内容 ID

内容 ID 与显示名称、MZ 数值槽位分离。中文标题可以修订，已发布 ID 不更名、不复用；删除内容保留废弃登记，不把其槽位分配给其他内容。

| 类型 | ID 约定 | 示例 |
| --- | --- | --- |
| 主线遭遇 | `cN-main-NN` | `c2-main-06` |
| 可选遭遇 | `cN-opt-NN` | `c2-opt-01` |
| 地图 | 章节＋地点，以剧情目录为准 | `c1-post` |
| 任务 | 章节任务或人物任务，以剧情目录为准 | `c2-side-01`、`he-lan-01` |
| 选择／事实 | 选择带章节，事实按语义登记，以剧情目录为准 | `c1-choice-contact`、`contact-address-kept` |
| 人物 | 固定角色标识 | `actor-linn` |
| 年表条目 | 章节＋事件标识 | `c2-timeline-pump-incident` |
| 技能／装备／结局 | 以系统清单或结局目录为准 | `fire-04`、`weapon-01`、`world-distributed` |

`EmbersRegistry.json` 登记稳定 ID、MZ 类别、数值 ID、章节、使用位置、状态和相互引用。插件启动时识别重复 ID 与不存在的引用；出现配置错误时阻止进入相关内容并明确错误，不能悄悄指向另一个条目。未来可由辅助脚本检查登记表，但本轮不生成登记表或脚本。

正式版每章六场主线、两场可选战斗，总计 42＋14；每章两场关键对决包含在六场主线内。53 个可学技能由 48 个基础技能与五个协作技能构成。救援、推进、抑制另设三个内部任务命令条目，属于目标战斗支撑，不计入可学技能图鉴；原生普攻、防御等系统条目也不占这 53 项。

### 4.2 开关、变量与公共事件分区

以下数字区间是未来工程保留范围，不要求一次填满。范围不足时按登记流程扩展，不能借用另一分区的空槽位。

| MZ 开关 | 用途 |
| --- | --- |
| 0001–0099 | 系统入口、菜单权限与流程状态 |
| 0100–0399 | 跨章节永久事实的事件页镜像 |
| 0400–1099 | 七章各 100 个章节事实与地图状态 |
| 1100–1499 | 同伴加入、任务、离队与生死状态镜像 |
| 1500–1999 | 支线、结局资格与后日谈镜像及预留 |

| MZ 变量 | 用途 |
| --- | --- |
| 0001–0049 | 章节、年份、年龄与公共流程结果；`V0010` 固定为最近战果 |
| 0050–0099 | 调查与资源显示镜像；钱币仍使用原生队伍金钱 |
| 0100–0239 | 七章各 20 个任务阶段／章节量化镜像 |
| 0240–0299 | 同伴任务阶段与人物状态镜像 |
| 0300–0499 | 额外显示、输入／返回值与预留 |

永久事实、任务、人物状态和年表以 `$gameSystem._embers` 为权威。登记为镜像的开关、变量只用于事件页与条件分支读取；修改必须调用剧情插件，插件同时刷新镜像。地图事件不能直接反向改写镜像，避免“日志说已经完成、事件却未完成”的双源问题。

地图自开关用于本地门、宝箱和事件表现；跨地图任务成果、首胜奖励、人物生死与结局资格不能只写自开关。公共事件保留系统、章节交接、人物、奖励与结束处理分区，按照同一登记表分配槽位。

### 4.3 统一事件模板

**调查事件：** 条件读取 → 必要背景 → 选项 → 单次提交事实／任务 → 年表 → 表现更新。长期结果使用稳定 ID，不把整段故事文本作为判断条件。

**关键选择：** 正文说明已知风险与替代方案 → 选择确认 → 提交确定结果 → 更新人物／地区 → 写年表 → 自动存档。只有明确会导致永久损失的选项显示额外确认；普通交涉不重复确认。

**地图战斗：** 检查是否已经首胜 → `ConfigureEncounter` → 原生“战斗处理” → 按最近战果调用公共事件 → 记录一次性成果／奖励 → 更新可见敌人 → 自动存档。

**章节交接：** 汇总本章目标 → 提示无法带入下一年龄阶段的任务 → 确认交接 → 推进年份／外观／据点状态 → 记录年表 → 传送下一章 → 自动存档。没有实时日历，也不靠等待推进年龄。

### 4.4 最低数据职责

完整字段与数值口径由系统规划定义，技术工程必须至少保持以下边界：

- 任务定义拥有合法阶段、前置、目标、一次性奖励与成果 ID。
- 遭遇定义拥有敌群、目标类型、时限、失败条件、环境修正、可否撤退、敌方行动计划、胜负公共事件。
- 角色定义区分已加入、待命、临时离队、永久离队与死亡；林恩与赫岚不得被不可恢复地移除主线基础队伍。
- 选择定义保存具体结果，不用统一善恶分数替代；互斥选择在登记表明确属于同一选择组。
- 结局读取已完成的任务与事实，计算资格，再由玩家从合法事业方向中选择。
- 事件重复触发、保存失败重试和地图重进都不得重新发放成果；使用稳定奖励收据检查。

## 5. 两个自有插件的职责与接口

### 5.1 `EmbersStory.js`：剧情状态、日志与保存协调

负责稳定 ID 登记、永久事实、任务阶段、人物状态、年表、一次性奖励收据及相关菜单窗口。只扩展必要窗口，不替换 MZ 的所有场景。

| 插件命令 | 最小参数 | 约定 |
| --- | --- | --- |
| `RecordFact` | `factId`、`sourceId` | 记录已发生事实；相同事实重复提交不产生新副作用 |
| `AdvanceQuest` | `questId`、`stageId`、`sourceId` | 只接受登记的合法阶段迁移，刷新镜像 |
| `SetActorStatus` | `actorId`、`statusId`、`sourceId` | 同步人物档案与原生队伍；永久死亡不能在当前进度被普通事件复活 |
| `AppendTimeline` | `entryId`、`variantId` | 加入与选择结果匹配的年表，单个事件不重复追加 |
| `GrantReward` | `rewardId`、`sourceId` | 发放登记奖励并记录收据；不接受事件传入任意金额 |
| `Checkpoint` | `checkpointId` | 保存当前已结算状态到自动槽位；失败时暂停后续剧情推进 |
| `OpenJournal` | `tabId` | 打开任务、人物或年表；关闭后返回原场景 |

`sourceId` 用于定位调用来自哪项选择、任务或遭遇，不作为玩家输入。年表标题与正文通过已登记模板解析；图像、对白和结果不依赖保存运行时对象引用。

普通数据库道具取得可以使用原生命令。含剧情资格、永久人物状态或首次奖励的操作必须经统一命令；地图作者不能通过大量“脚本”事件绕开其收据和合法阶段检查。

### 5.2 `EmbersBattle.js`：默认战斗上的目标扩展

负责遭遇配置、战前快照、目标 HUD、上下文任务动作、敌方预告、稳定行动顺序、结果返回与重试。使用默认队伍、敌群、角色、行动、伤害、状态、战斗动画和奖励窗口。

| 插件命令／数据出口 | 参数／内容 | 约定 |
| --- | --- | --- |
| `ConfigureEncounter` | `encounterId` | 从登记定义初始化下一场战斗并保存战前快照；紧跟原生“战斗处理” |
| `ClearEncounter` | 无 | 退出配置但未进入战斗时清理临时状态，不能清除已发奖励收据 |
| 最近战果 `V0010` | 0 未结算、1 胜利、2 失败、3 撤退 | 只由战斗插件写入，地图事件读取 |
| `battleResults[encounterId]` | 结果、失败原因、关键目标与首胜记录 | 返回地图后供剧情公共事件读取；不保存完整逐招日志 |
| 战斗界面“重试” | 使用本场快照 | 恢复初始人员、状态、目标与资源，不再次执行入场事件 |
| 战斗界面“返回准备” | 使用入场地图上下文 | 恢复本场未开始的状态，玩家可换队／整备后再次进入 |

事件作者不直接调用 `BattleManager` 私有方法。`ConfigureEncounter` 不自行启动第二套战斗，而是为随后的原生战斗处理设置上下文；未配置的开发测试战斗继续走原生行为。

### 5.3 目标动作与目标计量

目标动作通过上下文“任务”指令选择，其动作槽仍然属于当前角色的一次行动。三个内部命令条目只在相应遭遇出现，不进入探索菜单、技能学习或 53 项图鉴。

| 目标类型 | 控制内容 | 默认基线；遭遇可明确覆盖 |
| --- | --- | --- |
| 击退 `defeat` | 必须击倒的敌人列表 | 击倒全部指定敌人且至少一名队员可行动 |
| 救援 `rescue` | 救援进度、阻截者与回合限额 | 救援一次＋25，进度 100、清掉阻截者且不晚于第 10 回合结束 |
| 护送 `escort` | 独立 HP、路线进度 | 推进一次＋25，进度 100且目标 HP 大于 0 |
| 撤离 `evacuate` | 生存回合与主角可行动状态 | 守过四回合，林恩能够行动 |
| 压制 `suppress` | 压力、守稳回合、可击破核心 | 初始压力 3；抑制－2，下限 0；回合末压力大于 0 时＋1，已经压至 0 时不被动回涨；敌人干扰动作仍可加压；压力达到 8 失败；回合末检查压力为 0 连续三回合或击破核心胜利 |

这些是未经过玩法验证的初始设计数值，不作为未来平衡已通过的证据。实际任务界面必须显示该场采用的阈值和胜负条件。

护送目标不是第五名队员，不参加常规队伍治疗、目标选择或存档人物列表。通过遭遇的 `actionEffects` 将指定动作映射到目标计量，动作结束后一次更新；不能为了省代码创建一个可被替换进队的假同伴。

- 护送 HP 在开战时根据准备与装备初始化一次，不在重试中反复叠加。
- “护送阵”技能只减半下一次敌方护送攻击，单回合最多生效一次，不叠加；使用资格按岩术学习表确定，不限于赫岚。
- 普通治疗不恢复护送计量。独立应急维修在本场最多一次，消耗一份药品，恢复目标最大 HP 的 25%。
- 救援、推进与抑制采用内部任务动作；HP、MP、TP 和常规状态仍交给原生战斗结算。

同一动作先更新全部伤害、状态和目标计量，再判定结果。顺序为：明确不可挽回的任务失败 → 胜利且至少一名队员可行动 → 队伍全体失能 → 回合截止。护送 HP 归零与击倒关键敌人同时发生时仍然失败。关键对手越过阶段阈值后，下回合使用新计划，不在当前行动序列中突然插入额外攻击。

### 5.4 与原生生命周期的接合

技术实施采用少量明确钩子，记录每个钩子的用途和原始版本：

1. 原生战斗 `setup` 前加载遭遇上下文、记录快照；用标准回合入口建立队伍与敌群。
2. 输入阶段读取下一回合的已决定敌方计划；预告以动作类别、目标／候选范围和机制为主，不提前执行行动或消耗正式状态。
3. 行动排序处去掉速度随机项并使用冻结的排序规则；不改伤害计算与状态生命周期。
4. 每次行动结束更新一次 `actionEffects`，包括敌人干扰造成的加压。回合结束仅在压力大于 0 时执行被动＋1，再检查压力为 0 的连续稳定回合；非 0 时清零稳定计数。同时更新时限和护卫次数，再检查目标。
5. 对目标战斗挂接 `checkBattleEnd`：救援或护送尚未完成时，敌人全灭不能提前触发原生胜利；必要任务动作仍可继续执行。
6. 在统一结果处调用原生胜败／撤退处理；正常钱币／普通掉落与奖励窗口只走一次。
7. 回到地图后写最近战果与紧凑结果，由配置的公共事件办理剧情成果、特殊奖励和保存。

原生“战斗处理”必须启用可失败分支，避免普通战败直接进入游戏结束；可撤退项按遭遇配置开启。剧情悲剧终局通过明确选择事件进入，与普通战败相互独立。

允许撤退的场次采用 100% 成功的明确规则，禁用原生随机逃跑概率；关键战与已承诺的关键救援／护送段不可撤退，进入前说明。主动撤退保留已经消耗的药品、MP，无奖励；正常战败后的免费重试／返回准备才恢复战前快照，两者不能混用。

敌群原生 EXP 设为 0。主线首胜公共事件按系统规划的最低等级表，将队员经验补足到原生 `expForLevel` 对应值；已经达到该等级则不补，不另外创建经验曲线。时间跳跃按章节起始最低等级补足，可选战斗不发经验。该操作与其他首胜成果一样受收据保护，等级变化在结果提示中显示，不伪装成反复刷敌即可成长的机制。

插件不在战斗中提交永久剧情事实。战斗内显示的救援成果属于临时结果，返回地图成功结算时才转为事实、奖励和年表。这样重试恢复战前状态，不需要回滚半场已经执行的永久剧情。

### 5.5 战前快照与一次结算

快照至少包括：当前队伍与阵位、队员 HP／MP／TP／状态／增益、背包和三类资源、独立目标初始状态、遭遇 ID、进入地图与准备位置、可撤退设置和本场特殊条件。

快照只保存重试需要的明确字段，不把整个 `$gameSystem` 再嵌入 `$gameSystem._embers`，避免递归快照。正常战败的重试与返回准备均恢复本场药品消耗、战斗失能和临时计量；已在此前完成的任务、消费、人物选择不回退。

首胜成果由 `encounterId` 与 `rewardId` 收据共同保护。重复触发地图事件、重复打开奖励窗口或重试保存，只能读取同一已结算结果；胜利的钱币／普通掉落、等级保底和剧情奖励均不得重复发放。

## 6. 保存、失败处理与版本隔离

### 6.1 槽位与保存时点

- 五个手动槽位由玩家覆盖选择；自动槽位独立，不列作第六个手动槽。
- 地图安全场景允许手动保存。战斗、过场进行中、等待奖励结算和保存失败暂停期间不提供普通手动入口。
- 自动保存仅在章节交接、危险区入口和重大选择结算后触发；普通移动不逐步写盘。
- 保存角色、地图位置、章节／年份、任务、事实、人物状态、资源、年表与奖励收据；不保存动画队列、窗口对象或完整战斗日志。
- 不保存进行中的战斗；退出后从进入危险区前的检查点恢复，不提供半回合恢复承诺。

### 6.2 保存失败不会重新结算

剧情或战斗结果先在内存中一次结算，然后形成待保存内容；在写盘成功之前暂停后续事件。保存失败窗口提供重试及返回标题的明确说明：重试只再次写入同一份待保存内容，不能重新执行选择、战斗奖励、人物加入或年表追加。

旧的成功存档必须保留到新内容成功写入。未来保存适配采用临时写入、确认成功后替换的方式；保存成功才清理待写结果并恢复一次事件。若返回标题，告知未保存进度将丢失，由玩家确认后读取此前成功存档。

这与网页原型的“每动作写浏览器存储”不同。Windows 版本不引入多标签锁，也不要求每次普通战斗行动后写盘。

### 6.3 试玩与正式版本

存档记录 `projectId`、内容版本、存档结构版本和当前章节。试玩使用独立项目标识，不接受 React 存档，也不直接载入正式版进度。

试玩裁切跳过正式章节中的事件，其事实不完整，因此正式版从新游戏开始。玩家可保留试玩作为独立游戏；未来若另做试玩奖励兑换，只能传递一项明示的奖励资格，不能把试玩的章节、人物和年表当作完整正式进度。

正式版发布后，相同结构的补丁保留旧档；改变结构时显式制定迁移，未知版本不可静默覆盖。进入结构迁移前保留旧文件备份；未提供迁移时明确要求新游戏。

### 6.4 路径与安装包

试玩默认在可写目录解压运行，保存位置按冻结的 MZ 运行版本实测确定并写入说明。若正式版增加安装程序，应先实现并验收可写的用户保存目录，不能假定 `Program Files` 下能够保存。

不在规划阶段承诺已经支持所有 Windows 权限、云同步、杀毒软件或商店环境。首发只承诺经未来发布验收覆盖的 Windows 离线桌面运行方式。

| 核心选择 | 通信、证据、一次明确提示风险的选择 |
| 结果 | 两种事故救援结果，一个悲剧终局 |
| 系统 | 完整保存／读档、战败重试、简版年表与任务日志 |

制作顺序：六图灰盒与事件入口 → 年龄跳跃和同伴加入 → 五场战斗 → 两项支线与结果变体 → 关键选择与年表 → 正式试玩素材和声音替换 → 人工节奏调整。

60–90 分钟是未来人工试玩的目标，不能用自动运行时长或对白估字证明。试玩结尾必须让玩家看到至少两项早期行为对救援和人物对白的影响。

## 9. 依赖、瓶颈与风险控制

| 风险／瓶颈 | 对项目的影响 | 固定处理方式 |
| --- | --- | --- |
| 过早扩充章节 | 剧情、技术与素材同时返工 | M1 引擎冻结、M2 试玩通过后再扩展 |
| 原生战斗与插件冲突 | 目标被提前胜利、结果重复 | 两个自有插件，记录钩子；不叠加多个改写战斗的第三方插件 |
| 长期因果缺少实际反馈 | 选择只剩对白差异 | 每条因果在任务、通路、资源、人物或结局中产生明确效果 |
| 内容 ID／槽位碰撞 | 读档指向错误内容 | 追加登记、不复用、单负责人分配、镜像分区 |
| 同伴永久损失破坏通关 | 队伍缺功能形成软锁 | 保底林恩与赫岚；损失前说明替代路线与风险 |
| 资源耗尽 | 玩家无法推进 | 主线提供劳动、交涉或较长路线，不强迫刷钱 |
| 素材规模被低估 | 只有占位能跑，正式版迟迟未完成 | 将占位替换、年龄外观和战斗动作列作独立交付 |
| 已购素材引擎限制 | 改选 Godot 后不能继续使用 | 按台账复核，优先原创或可跨引擎授权素材 |
| 保存失败重放剧情 | 重复发奖励或人物状态错乱 | 固定待保存内容，重试仅写盘、成功后单次恢复 |
| 未知开发人力 | 虚假工期与承诺 | 用原型与试玩实际耗时估算后续，不预报未经支持的日期 |

最大的持续工作量是地图事件、人物阶段素材与分支内容，而非安装引擎。每章需同时具备任务、战斗、反馈和交接；技术原型只能降低引擎风险，不能替代内容制作。

## 10. 未来验收范围；本轮不执行

用户已明确本轮不进行验证，也没有相关开发资源，因此下面只定义未来 Windows 开发时的交付判据。本文不宣称这些检查已经运行或通过。

### 10.1 后续可自动检查的部分

- 登记表中 ID 唯一、引用存在、废弃槽位不复用；主线数量、技能分类与结局条件可追溯。
- 任务阶段迁移、互斥事实、首胜及奖励幂等、年表去重。
- 五类目标的边界：同击倒与护送归零、最后行动救援完成、全体失能、回合上限、压力与核心击破。
- 快照重试恢复药品、HP、MP、TP 与独立目标，不回退此前任务、不重复奖励。
- 保存失败后重试使用同一待写内容；试玩／正式存档及未知版本不能互相覆盖。

这些属于未来技术原型的行为检查，不要求给每个普通地图事件机械地增加测试。

### 10.2 必须人工验收的部分

- 年龄跳跃、人物加入、死亡／离队后对白与年表一致。
- 三条核心因果分别以完整准备、部分准备和补救路线游玩，玩家理解实际后果。
- 五类任务目标与界面说明一致；敌方预告可理解，不暗示未确定的精确结果。
- 主线以基本等级与装备完成；缺钱、补给不足、可选同伴失去时有可推进路线。
- 在未来实际 Windows 机器导出后进行离线启动、窗口／全屏、中文路径、键鼠和保存失败场景验收。
- 原创角色年龄外观、侧视动作、地图遮挡、音量与必要文字达到可读条件。
- 记录人工游玩时长、失败次数与理解问题；分别确认试玩 60–90 分钟和正式版 12–16 小时目标。
