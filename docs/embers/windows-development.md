# 《余烬来信》Windows Godot＋Rust 制作与交接方案

> 当前交付仅为详细规划。未创建引擎工程、编写 Rust／GDScript 代码、安装工具、制作素材、运行检查或导出游戏。本文保留原文件名以维持文档链接，内容完整采用 Godot＋Rust 路线。

配套依据：[游戏设定](game-design.md)、[剧情与任务](story-and-quests.md)、[系统与数据](systems-and-data.md)、[Godot＋Rust 架构与接口](godot-rust-architecture.md)。玩法、任务条件与公共接口分别以对应文档为准；本文规定 Windows 建项、编辑器工作流、制作依赖与交付方式，不另建第二套接口。

## 1. 技术路线与职责

正式工程采用 Godot 4 稳定标准版、Rust 和社区 godot-rust／gdext 的 `godot` crate，通过 GDExtension 加载原生动态库。Godot 负责场景、地图、碰撞、界面、动画、声音与输入；Rust 负责规则、权威进度、内容解析和保存协调。首发平台为 Windows x86_64 离线单机，渲染采用 Compatibility。

GDExtension 允许 Godot 在运行时使用原生共享库，不要求重编译引擎；Rust 绑定由社区 gdext 提供，不能将其称为 Godot 内置的 Rust 脚本语言。[Godot GDExtension 概览](https://docs.godotengine.org/en/stable/engine_details/engine_api/gdextension/index.html)、[gdext 入门](https://godot-rust.github.io/book/intro/)

| 层 | 具体交付 | 边界 |
| --- | --- | --- |
| `embers-core` | 人物、战斗、目标、任务、事实、奖励、结局、等级与存档 DTO | 纯 Rust；不依赖 Godot，不访问磁盘，不持有节点或资源对象 |
| `embers-godot` | `cdylib`、`EmbersSession` 节点、JSON 边界、主线程信号、`SaveRepository` | 桥接核心与 Godot；只在这一层做 Godot API 调用和存档 IO |
| `embers-tools` | 内容处理、目录打包、引用检查等未来命令行工具 | 可执行程序；复用 core 内容模型，不参与玩家运行流程 |
| Godot 工程 | 地图、Control 界面、Sprite2D、动画、音频、输入与场景切换 | 少量 GDScript 做展示编排；读取视图、发送命令，不计算伤害或发奖 |
| 内容目录 | UTF-8 JSON、稳定内容 ID、对白与数值表 | 内容作者编辑；转换为运行 catalog，不存引擎对象引用 |
| 素材目录 | 原创图像、声音与源文件、授权台账 | 显示资源与规则数据分离，以稳定资源 ID 连接 |

不加入 JavaScript、C#、Bevy、ECS 框架、自制渲染器或第二套战斗引擎。Godot 不提供本项目现成的 RPG 数据库、回合规则或完整存档系统；这些属于上述模块的实际制作任务。

### 1.1 与当前仓库的关系

设计参考点为 main 提交 `c1dc162`。沿用七章成长、长期因果、目标战斗、年表、一次性奖励与失败重试等经验；新游戏不搬入 React 组件、卡牌抽洗牌、网页存档、多标签锁、Docker 流程或原作人物立绘。

当前仓库继续作为规划与旧网页原型的资料库。未来 Windows 上建立独立 Godot＋Rust 工程，避免把 Rust 构建目录混入现有前端项目。旧网页存档不能导入新游戏。

### 1.2 固定制作规模

| 内容 | 正式版基线 |
| --- | ---: |
| 章节 | 7，年龄 8、15、18、23、28、33、40 |
| 可玩地图 | 40，各章 6、5、7、7、5、5、5 |
| 主线／可选战斗 | 42／14，每章 6／2 |
| 关键对决 | 14，包含在主线内 |
| 地区支线／同伴任务 | 14／15 |

救援、推进、抑制是战斗上下文动作，由核心动作类型表达，不挤占 53 项可学技能，也不借用某个引擎数据库槽位。上述数字是制作预算，不表示资源或关卡已存在。

## 2. Windows 工具链与版本锁定

### 2.1 未来准备的开发资源

| 资源 | 选定方式 | 用途 |
| --- | --- | --- |
| Godot | 官方 Godot 4 稳定标准版；API 至少 4.3，以满足 TileMapLayer 等本项目能力 | 编辑器、运行程序与 2D 场景 |
| 导出模板 | 与冻结编辑器版本匹配 | Windows Desktop 导出 |
| Rust | rustup 管理的稳定工具链；建项时记录确切版本 | 编译 workspace 与工具 |
| Windows 编译链 | Visual Studio Build Tools 的 MSVC x64 工具及 Windows SDK | `x86_64-pc-windows-msvc` 链接与构建 |
| Rust 绑定 | crates.io 发布的 `godot` crate，锁定确切版本和匹配 API feature | GDExtension 桥接 |
| Git | 工程版本控制；大型素材源文件使用 Git LFS | 代码、场景、内容与素材版本 |

Rust 的 MSVC 目标需要链接器和 Windows 库，官方安装说明列出 C++ 桌面开发工作负载及可单独选择的 MSVC／SDK 组件。采用该工具链不意味着要用 C++ 实现游戏。[rustup MSVC 前置资源](https://rust-lang.github.io/rustup/installation/windows-msvc.html)

不在本轮下载上述资源，不记录未经核实的未来“最新版本”，也不承诺未知开发机的最低硬件配置。Godot 编辑器、API 等级、crate、Rust 工具链和导出模板要作为同一组兼容版本冻结，而不是分别追随更新。

### 2.2 建项时必须记录的版本组合

工程版本记录至少包含：Godot 完整版本与标准构建类型、Compatibility 渲染、Windows 导出模板版本、`godot` crate 确切版本、单一 `api-4-*` feature、Rust 确切版本、MSVC／SDK 和目标架构。

`Cargo.lock` 提交到 Git；`rust-toolchain.toml` 固定 Rust 工具链，Cargo manifest 固定 `godot` crate 与 API feature。不能依赖 crate 的默认 API 在后续升级中保持相同。冻结的 API 必须与运行 Godot 兼容；gdext 区分编译 API 版本与运行引擎版本。[gdext Godot 版本选择](https://godot-rust.github.io/book/toolchain/godot-version.html)、[兼容性说明](https://godot-rust.github.io/book/toolchain/compatibility.html)

具体兼容组合在未来 Windows 技术原型启动时按届时官方资料确定，再写入工程。首版不使用 `api-custom`、Godot 开发版、引擎分叉或从绑定 master 分支直接取依赖。

升级只安排在里程碑边界。先保存旧工程标签和发布包，再按新组合重建 DLL、重新导出与验收；不让机器自动升级改变正在制作的基线。

## 3. 未来工程目录与版本管理

### 3.1 目录约定

未来工作路径使用简短英文名，例如 `D:\Games\EmbersLetter`。以下是待建立的工程结构，不是本轮新增文件清单。

```text
EmbersLetter/
  game/
    project.godot
    scenes/               地图、战斗、菜单、可复用节点场景
    scripts/              少量展示与输入 GDScript
    assets/               导入游戏的图像、声音、字体
    content/              运行 catalog 与表现资源映射
    extensions/
      embers.gdextension
      bin/windows/debug/  暂存开发 DLL
      bin/windows/release/暂存发布 DLL
  rust/
    Cargo.toml            workspace
    Cargo.lock
    rust-toolchain.toml
    crates/
      embers-core/
      embers-godot/
      embers-tools/
  content/json/           可编辑的规则、对白、任务与遭遇定义
  source-assets/          美术、音乐与音效源文件
  asset-register/         素材来源与使用记录
  tools/                  未来构建、内容暂存与发布脚本
  design/                 已冻结规划、授权与生产记录
  releases/               导出包与版本说明
```

Rust 与 Godot 目录分开，Godot 不扫描 `rust/target` 中的 `.obj`、缓存和构建产物。运行时使用的内容与 DLL 暂存进 `game/` 内部后再导出，不让最终包依赖工程外部相对路径。gdext 官方入门说明要求导出扩展库路径位于 `res://` 内部。[gdext 工程结构与扩展连接](https://godot-rust.github.io/book/intro/hello-world.html)

`content/json/` 是人工维护的唯一内容源。未来 `embers-tools` 处理后写入 `game/content/`；该暂存目录不能成为第二份手工修改的数据源。构建记录保存 catalog 的内容版本与源提交，避免 DLL 和数据分别来自不同版本。

导出后的运行内容可能在 PCK 中，由桥接使用 Godot FileAccess 读取成字符串后交给 core。Rust `std::fs` 只处理已转换成操作系统路径的用户存档，不能把 `res://` 内容当作外部普通文件打开。

### 3.2 Git 与协作边界

- 提交 Rust 源文件、锁文件、Godot 项目／场景／资源定义、内容 JSON、原图及导入参数、架构和授权记录。
- 忽略 `rust/target/`、Godot 导入缓存、个人存档、导出目录和临时日志；按冻结 Godot 版本保留需要版本化的资源标识文件，不把“所有隐藏文件”一概忽略。
- 发布包记录 Git 提交、内容版本、核心版本与 DLL 构建模式；没有对应来源的 DLL 不作为正式交付。
- 同一地图 `.tscn`、TileSet 或关键 UI 场景指定单一编辑者，减少场景文本冲突；规则 JSON 可以按任务／章节拆分协作。
- 大型源文件默认使用 Git LFS，另保留素材备份；版本控制不代替备份。
- 临时开发地图、测试内容和正式 catalog 有明确构建范围，不能在发布包里残留直达结局的调试入口。

## 4. GDExtension 构建、装载与 DLL 交接

### 4.1 最小装载链

未来 `embers-godot` 以 `cdylib` 生成 Windows DLL，并注册继承 Node 的 `EmbersSession`。Godot 工程将该节点作为名为 `GameSession` 的 Autoload，只有它持有活动会话、内容目录和保存协调器。

首个装载原型只证明三件事：Godot 能识别 Rust 节点；节点能按架构解析初始化与视图请求；返回值和错误能经主线程信号进入一个最小 Control 窗口。不先制作完整战斗界面再排查 DLL 装载。

编辑器打开工程和 Inspector 预览不初始化人生、不推进任务、不写存档；`initialize` 只装入并核验内容，人生由玩家的新游戏命令建立。

公开方法、信号、JSON envelope 和错误结构统一以 [架构与接口](godot-rust-architecture.md) 为准。Godot 页面通过该边界初始化、发送命令、读取视图、列举／保存／加载槽位和重试待写结果，不直接取 Rust 内部字段。

### 4.2 `.gdextension` 的设置要求

| 项目 | 本项目约定 |
| --- | --- |
| 初始化入口 | `gdext_rust_init`，沿用 gdext 默认 Rust 扩展入口，不另设自定义名称 |
| 兼容下限 | 与已锁定 API 等级相符，不随意抄旧教程里的版本 |
| 开发库选择 | `windows.debug.x86_64` 指向 `res://extensions/bin/windows/debug/embers_godot.dll` |
| 发布库选择 | `windows.release.x86_64` 指向 `res://extensions/bin/windows/release/embers_godot.dll` |
| 重载 | 首版关闭扩展热重载，使用关闭进程后重建的流程 |
| 依赖 | 若 DLL 有额外原生依赖，明确登记其导出位置和来源，不靠开发机 PATH 补齐 |

GDExtension 配置的 feature 标签决定装载和导出匹配的共享库；debug 与 release 路径必须分别准确，扩展文件本身不会替开发者运行 Cargo 构建。[Godot `.gdextension` 配置](https://docs.godotengine.org/en/stable/engine_details/engine_api/gdextension/gdextension_file.html)

以上 DLL 路径、`embers_godot` 库名与初始化入口是固定工程约定，最小装载阶段据此配置并记录实际版本。不得把 `rust/target` 当作已经导出的扩展库，或者认为只要编辑器能加载 debug DLL，release 包自然也完整。

### 4.3 开发和发布的重建顺序

1. 关闭编辑器和仍在运行的游戏进程，确认 DLL 没有被当前工作进程占用。
2. 用冻结工具链构建对应 target 与 profile。
3. 将该次 `embers-godot` DLL 暂存到匹配的 `game/extensions/bin/windows/` 子目录，记录构建来源。
4. 内容工具暂存同版本 catalog 与资源映射；不把旧 catalog 和新 DLL 混合。
5. 重新打开 Godot，处理扩展载入错误后继续编辑；发布时使用 release 扩展和匹配导出模板。

关闭进程再重编译是首版的固定工作流，不要求开发人员依赖热重载能力。仅修改对白或场景一般不必重建 Rust；改变 core 规则、桥接字段或内容结构时必须重建相应组件并重新暂存。

### 4.4 主线程和故障边界

桥接调用、节点访问、资源操作和信号发出只在 Godot 主线程进行。核心保持与场景树无关，首版不增加异步命令线程来提升不存在的性能瓶颈。

解析失败、未知内容 ID、规则拒绝、版本不兼容和保存失败按架构返回明确错误。Godot 不收到有效返回就假定命令成功，不在错误分支自行补发奖励或改变人物状态。Rust 错误不能穿越 FFI 变成未处理崩溃；桥接错误处理是技术原型的一项实际工作。

## 5. 场景与内容作者的工作流

### 5.1 Godot 提供的制作工具

地图作者使用 TileSet／TileMapLayer 绘制 48×48 正交地图，配置场景几何碰撞、装饰和光效。人物由 Sprite2D／AnimatedSprite2D、AnimationPlayer 与碰撞节点组成；界面使用 Control、容器、锚点和主题资源。

引擎负责可见表现与空间碰撞，任务是否可接、门是否因剧情封闭、敌人是否已首胜、人物是否还活着由 core 状态决定。地图上一个事件不能凭场景自存布尔值定义永久任务成果。

### 5.2 交互节点与稳定内容 ID

建立少量可复用场景：调查点、人物对话点、地图出口、可见敌人、资源点与安全据点。作者在 Inspector 填登记的 `interaction_id`／出口 ID，再配置头像、显示图和动画。

交互进入时查询 `GameSession` 的可用视图，显示正文、条件与选项；选择后只发送架构定义的命令。对应事实、任务阶段、物品和人物状态由 core 一次结算，Godot 据新视图刷新表现。

未登记 ID、悬空对白、缺失资源映射在开发模式明显报告，不能静默显示另一个人物或让关键门变成可通行。正式包遇到内容错误应说明无法继续该交互并保留既有存档，不能自动跳过主线。

### 5.3 地图位置与移动边界

探索采用四向网格移动。Godot 的 CharacterBody2D 负责场景碰撞和格间插值，每格移动结束发送 `RecordPosition`；core 检查当前地图、坐标边界、相邻关系与剧情封路条件，再更新 `CampaignState`。

地图间移动发送 `MoveToMap` 的出口 ID，由 core 验证出口解锁与目标地图。界面不能直接传任意地图 ID 绕过章节。位置命令不是每帧调用；停格且位置提交成功后才开放交互、菜单与保存。

移动被拒绝时，Godot 回到已确认格并显示原因。读档位置从 `CampaignState` 恢复，保存不临时读取玩家节点坐标补写另一份位置。几何碰撞仍属于 Godot，剧情门与出口资格仍属于 core，二者不能互相代替。

### 5.4 战斗界面不是规则引擎

Godot 显示队伍、敌人、状态、目标计量和敌方意图，收集本回合每名可行动队员的选择，然后一次发送 `SubmitTurn`。core 验证整队动作、稳定排序，计算伤害／状态／独立目标和胜负，产生候选状态及有序演出事件。

Godot 播放命中、受击、治疗、目标变化和结果演出，不重新计算数值。动画结束、跳过、窗口切换或音效失败不会改变已经结算的回合；界面播放期间锁定下一回合提交，结束后以新视图继续。

任务动作、护送独立 HP、压力和首胜奖励全部属于 core。不能通过 AnimationPlayer 的回调减生命、弹窗关闭时发钱，或由场景自行判断敌人倒下就是胜利。一次动作完成后再判定目标；一整回合虽可包含多段动画，领域结算只发生一次。

### 5.5 编辑与显示同步

- 任务、对白、遭遇、选择、奖励与结局在 `content/json/` 编辑，以英文稳定 ID 连接。
- 中文显示名可以修订，已发布 ID 不复用；废弃 ID 保留登记，读档不会指向新内容。
- 图片、动画、声音与字体通过独立资源映射连接；core 不存 `res://` 节点路径作为剧情事实。
- 章节交接、永久损失和首胜成果统一走 core 命令；普通场景脚本只编排展示。
- 任务／人物／年表从当前视图刷新，不各自持有可修改的进度副本。
- `embers-tools` 的未来内容处理检查是生产工具，不用于在本轮生成或执行游戏工程。

## 6. 保存协调与交付约束

### 6.1 保存的职责

`CampaignState` 持有人物 HP／MP、技能、装备、背包、钱币、补给、药品、任务、事实、年表、人物可用状态、章节年份与已提交地图位置。持久存档采用纯 JSON `SaveDto`，只包含可恢复的长期进度、版本、revision 和一次性奖励收据，不包含活动 `BattleState`、重试快照、动画队列、Godot Node、Resource、RID 或对象引用。

`SaveRepository` 只存在于 `embers-godot`。桥接使用 Godot 的 `ProjectSettings.globalize_path` 将 `user://` 转换成实际用户目录，再做文件 IO；core 只接受解析后的 DTO，不知道文件保存在哪里。[ProjectSettings 路径转换](https://docs.godotengine.org/en/stable/classes/class_projectsettings.html)

五个手动槽和自动槽隔离。地图停格后可手动保存；战斗、领域命令处理中与必存结果待写期间不提供普通保存入口。战斗不提供半回合存档，退出后从战前入口检查点重开。

### 6.2 候选先落盘、后发布

core 处理命令返回候选状态、演出事件和检查点意图。`StartBattle` 前、重大选择、章节交接和战斗成果等必存检查点，桥接必须先成功写入候选的持久 DTO，再替换当前已发布状态、发送状态变化信号并播放事件。战斗内存状态不因为该检查点而写入 durable DTO。

写入失败时持有同一 `PendingCommit` 和固定字节，冻结后续领域命令；界面显示保存失败。`retry_pending_save()` 只重新写入同一候选，不再调用领域结算，不改变掉落、年表或人物结果。旧成功存档保留，成功后只发布一次。

手动保存失败同样冻结后续领域命令，但不撤销已经发布的当前状态；重试写相同字节，不重演上一命令。等待期间允许读当前视图与存档列表。玩家确认放弃待写内容和未保存进度后，才可读其他槽位或返回标题；具体方法与错误封套按架构合同处理。

### 6.3 A／B 双代文件

每个逻辑槽位使用 A、B 两个持久代文件，界面仍然只有五个手动和一个自动槽。写入选择非当前有效代，先写临时文件并 `sync_all`，再替换该非当前代；成功后才提交，当前有效代始终保留，不先删除。

这避免依赖“直接覆盖当前存档一定原子成功”的假设。首版不新增 Windows 专用文件替换绑定，具体命名、有效性判定、generation 和错误恢复完全按 `SaveRepository` 合同执行。

同版本读取最高有效且兼容的 generation。发现更新存档结构版本时隔离并提示，不擅自降级加载旧代再覆盖新文件。双代与临时写降低损坏风险，不作为断电绝对可靠的承诺；未来需要覆盖对应失败场景。

### 6.4 战斗快照与奖励

战前快照由 core 在内存保存队伍、阵位、生命／魔力／状态、资源、遭遇和独立目标初值。失败后的重试或返回准备恢复本场初始状态，保留此前已经完成的任务；主动撤退则保留本次已消耗的药品和 MP，无奖励。

首次胜利奖励、主线最低等级经验补差、任务成果和年表由 core 集中处理并保存收据。桥接和 Godot 都不能第二次发放。主线等级保底调用核心 `LevelCurve`，不依赖引擎内置经验公式；详细策略以系统规划为准。

### 6.5 试玩与正式存档

试玩使用独立项目标识和用户保存子目录，与正式版隔离。它裁切了章节中段，不能直接迁移为完整正式进度，也不接受网页存档。

结构不兼容或未知版本的槽位给出明确说明并保留原文件，不静默覆盖。正式版发布后改变存档结构，需要独立迁移方案与旧文件备份；没有迁移时说明必须新开游戏。

## 7. 资源规格与原创素材交接

### 7.1 Godot 原生资源方案

保留正交 48×48 地图格和侧视战斗。资源按 Godot 的 TileSet、AtlasTexture、SpriteFrames 和 AnimationPlayer 定义，图集布局由资源清单声明，不强制固定整图排布。

| 资源 | 项目交付规格 |
| --- | --- |
| 地图图块 | 48×48 格；图集布局由 TileSet 声明，含碰撞、地形连接与资源 ID |
| 行走人物 | 四方向、待机与行走动画；48×48 基础帧，底部脚点一致；帧数和时间写入 SpriteFrames |
| 侧视队员 | 固定锚点；待机、移动、普攻、施术、护卫、受击、状态、胜利、失能动画按名称登记 |
| 战斗敌人 | Sprite2D 静态图或具名动画；尺寸由构图确定，不要求套用队员同一帧表 |
| 对话头像 | 原创手绘透明 PNG，建议交付 512×512 源导出，界面统一裁切缩放 |

像素地图和人物采用最近邻过滤，不用模糊插值掩盖边缘；手绘头像与背景单独设定适合的过滤。图片源文件、导入参数和运行贴图一起可追溯。Godot 支持图片导入与相应纹理设置，项目的帧规格与命名由制作清单明确。[Godot 图片导入](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_images.html)

地图使用整数格坐标，动画中的浮点位置只属于表现。画面布局采用架构规定的 1280×720 基准，Control 通过容器与锚点适应窗口；最终可读性在未来技术原型阶段确认。核心必要文本不得仅靠极小像素字体或悬停显示。

### 7.2 素材规模和制作顺序

林恩拥有儿童、青年、成年三个阶段；五位同伴各有加入期与后期两个阶段，共 13 组主要人物外观。每组需要行走、头像和侧视资源，可复用动作模板，但不能只更改名字表示年龄变化。

试玩只完成林恩儿童／青年、赫岚和米娅加入期以及五场战斗实际需要的敌人。正式版逐章扩展，普通敌人可复用行为与动作骨架，关键对手优先制作清晰机制表现。

先完成可复用地形、人物基础动作、字体与核心 UI，再制作专用场景和额外表情。正式版十首循环音乐和三首短结局曲通过主题变奏表现变化，不制作全语音。试玩四首循环音乐分别用于故乡、道路、危险区和战斗。

临时图、默认形状和占位声音必须标记 `placeholder`。可运行的占位原型不代表原创美术已经完成；替换占位是试玩与发布里程碑中的独立交付。

### 7.3 资源台账

每项素材登记资源 ID、文件、用途、作者／提供方、来源、取得日期、许可、商用／修改／署名要求、原始凭据、源文件位置和占位／正式状态。

- 自制和外包素材保留源文件与作者约定，明确游戏使用、修改和分发范围。
- 外购资源按各自许可使用；引擎限定素材不能默认转入本工程。
- 原作人物、标志、立绘与现有网页的原作参考不进入原创正式版。
- 开源依赖、Godot 与字体等按其许可汇总必要通知和署名；不把拥有源码当作没有许可要求。
- 未来若使用生成服务，保留来源与当时条款，进行风格和边缘整理；本轮不生成图片或下载素材。

## 9. 导出与故障排查交接

### 9.1 发布包的必要组成

Windows Desktop 预设固定 x86_64、release 模式、Compatibility、匹配模板。发布目录需要运行 EXE、PCK、由 GDExtension 导出的 release DLL、必要依赖与版本／许可说明。源 `.tscn`、catalog 和导入资源按导出预设进入 PCK；原生 DLL 是单独需要确认的运行依赖。

内容 JSON、动态资源映射和扩展目录显式纳入导出范围，不能完全依赖场景引用自动收集。导出只读资源使用 `res://`，存档写 `user://`，不写入 EXE 所在目录。

玩家不需要 Godot 编辑器、Rust、Cargo 或 Visual Studio。若实际构建依赖系统运行组件，记录并安排正常发行方式；不能让玩家安装整套开发工具补齐发布缺失。

### 9.2 常见故障定位顺序

| 症状 | 首先定位 |
| --- | --- |
| Rust 节点不存在 | 扩展文件、DLL 路径、入口、架构与版本组合 |
| 编辑器成功，导出失败 | release DLL 是否构建／暂存，feature 路径与导出模板 |
| 本机可运行，新机器失败 | 包内 DLL／依赖、catalog 和动态资源是否齐全 |
| DLL 无法覆盖 | 编辑器或游戏进程是否仍占用；关闭后重建 |
| 交互没有进度变化 | content ID、core 命令返回、拒绝原因与当前 revision |
| 视觉位置与读档位置不一致 | 是否停格提交 RecordPosition，是否误从节点保存 |
| 动画跳过后重复奖励 | Godot 是否越界发奖，core 收据与单次命令是否被绕过 |
| 保存失败后选择重新出现 | 候选是否过早发布，是否丢失 PendingCommit |

日志区分配置、内容、规则拒绝与 IO 错误，不把全部失败显示为“未知错误”。调试信息帮助作者定位 ID 与版本，玩家界面不暴露无关实现细节。

## 10. 未来验收计划；本轮不执行

用户本轮只需要详细规划，没有相关开发资源。以下仅列未来实施的必要交付判据，不表示已经检查通过。

### 10.1 Rust 与内容层

- 未来按 workspace 执行 `cargo check`、`cargo test`、格式检查及 `cargo clippy`；DLL 构建使用锁定依赖与目标。

## 11. 风险与实施清单

| 风险 | 处理方式 |
| --- | --- |
| Rust／Godot 双边各保存一份规则 | core 唯一权威；Godot 只收集命令和播放事件 |
| 绑定与 API 组合不兼容 | 冻结兼容版本组，先完成最小装载再制作内容 |
| release 包漏 DLL 或内容 | 显式暂存、导出与独立机器验收，不依赖 target 目录 |
| DLL 占用与热重载问题 | 首版关闭热重载，关闭所有相关进程后重编译 |
| JSON 桥接失控增大接口 | 单一 GameSession 合同，不给每个菜单新增旁路 |
| 保存失败发布半成品结果 | 候选先落盘；PendingCommit 重写，不重新结算 |
| 素材与章节同时铺开 | 完成 core／bridge／试玩，再逐章扩展 |
| 内容 ID 更名破坏存档 | 显示名可改，稳定 ID 不复用，迁移另立方案 |
| 占位可运行被当作正式完成 | 素材替换与授权列入独立里程碑 |
